# 에이전트 진단 (1단계)

에이전트를 켠 상태와 끈 상태로 같은 시나리오를 실제로 실행해, 에이전트가 규칙 대비 무엇을 더했는지, 호출이 어디서 낭비되는지, 화면에서 그 차이가 보이는지를 기록했습니다. 이 단계에서는 코드를 고치지 않았습니다.

## 방법

- 실행일: 2026-09-26. 모델: `bedrock-gpt-5.6-sol`(LiteLLM 게이트웨이).
- `.env`는 열거나 출력하지 않고 그대로 읽었고, 실행 환경에서 `REPLAN_PAID_CALLS_ENABLED`만 `true`/`false`로 덮어썼습니다. 각 실행은 새 `REPLAN_DATA_DIR`에서 진행해 기존 `.data`는 건드리지 않았습니다.
- API와 worker를 프로세스 안에서 그대로 띄우고 웹 화면과 같은 순서로 호출했습니다: 프로젝트 생성 → hero 기준 일정 연결 → 통보 등록 → 잠정 분석(`preview_only: true`) → 해석 확인 → 정식 분석. V08은 사람이 T036·2026-01-15를 지정했습니다. 외부 신호는 감시 계획을 켜고 수집을 한 번 실행했습니다.
- LLM 호출은 게이트웨이 HTTP 요청 단위로 기록했습니다(요청·응답 본문, 도구 호출, 토큰, 게이트웨이가 돌려준 `x-litellm-response-cost`). 호출 상한 40회를 코드로 강제했습니다.
- 외부 수집: 공휴일은 저장소의 `data/external/*-holidays.json` 스냅숏을 썼고, 등록 공지는 감사용 합성 공지 1건(EU 배터리 설비 문서 요건, 효력일 2026-11-01, "30일 검토 가능")을 넣었습니다. 기상 수집은 끄고 실행했습니다.
- 화면: 각 실행의 데이터로 웹 앱을 띄워 Playwright로 변경 카드와 대응안 화면의 '에이전트 판단 과정'을 캡처했습니다.
- `scripts/evaluate_agent_real.py`는 실행하지 않았습니다.
- 원자료는 커밋하지 않는 `artifacts/agent_audit/`에 있습니다: `<시나리오>_<on|off>/llm_calls.json`(요청·응답), `api_trace.json`, `result.json`(실행 결과·호출 수·토큰), `project_*.json`(단계별 화면 데이터), `screens/`(캡처와 화면 텍스트), `harness.py`(재실행 스크립트).

## 찾아본 항목별 결과

### 불필요한 LLM 호출

- **잠정 분석에서 에이전트가 전부 실행됩니다.** 웹은 통보를 등록하자마자 `preview_only: true`로 분석을 만들고(`apps/web/app/workspace.tsx:333`), 해석 확인 후 다시 정식 분석을 만듭니다(`workspace.tsx:376`). API는 이 값을 저장만 하고(`services/api/app/main.py:909`) 워커는 읽지 않아(`services/api/app/worker.py:305` 이하) 두 번 모두 같은 에이전트 루프를 돕니다. H04·H02·V08에서 5회, $1.198(전체 비용의 37%)가 정식 분석에서 다시 계산되는 잠정 결과에 쓰였습니다. H04는 이 때문에 통보 카드가 30초간 `해석 중`으로 멈춰 있었습니다(규칙은 1초 안에 T045·날짜를 이미 추출).
- **외부 변화 감지 시 유료 분석이 자동 실행됩니다**(`worker.py:675`). 사람이 근거를 보기 전에 에이전트가 돌고, 달력 7개를 켠 기본 감시 계획에서는 수집 한 번에 분석 7건이 생깁니다(끈 상태 실행으로 확인).
- **V08 잠정 분석의 에이전트 호출**은 작업 후보 검색이 이미 만든 질문을 다시 쓴 것뿐입니다.

### 규칙으로 충분한데 LLM을 쓰는 곳

- H04·H02처럼 통보에 작업 ID와 날짜가 모두 있으면 해석은 규칙이 끝냅니다. 에이전트는 무대응 재점검을 한 번 더 부르고, 계산 결과를 다시 타이핑합니다(`impacted_tasks` 19개, `options` 6개, `summary` 객체). 이 필드들은 화면에 쓰이지 않거나(`impacted_tasks`, `options`, `required_actions`) 템플릿 문장으로 대체됩니다(`summary`, `services/api/app/agent/runtime.py:420`). H04 정식 분석의 마지막 응답 출력 3,227 토큰 대부분이 여기에 쓰였습니다.
- 공휴일 중첩은 결정적 계산이라 에이전트가 더할 해석이 없는데도 자동 실행됐습니다.
- 감시 계획 보강은 규칙 제안에 일반적인 문장을 더하는 수준입니다.
- 반대로 LLM이 규칙보다 분명히 나았던 곳은 **V08 작업 연결**과 **공지 후보 축소(39→7)** 두 곳입니다. 둘 다 에이전트 루프가 아니라 1회 호출(`retrieve_related_tasks`, `interpret_notice`)이었습니다.

### 토큰이 몰리는 곳

- `recheck_shifted_schedule` 도구 결과가 22.7만~25.8만 자입니다. 이 중 `schedule`(10.7만 자)과 `supplier_schedule`(10.7만 자) 두 배열이 94%입니다. 이 결과를 받은 마지막 응답 5회가 입력 369,873 토큰(전체의 86%), 비용 $2.81(86%)입니다.
- 게이트웨이가 이 긴 입력을 매번 캐시 쓰기로 과금했지만(호출당 약 $0.50) 다시 읽힌 적은 없습니다(캐시 읽기 토큰 합계 23,366).
- `get_project_context`는 작업 64개 전체(8.9천 자)를 돌려주는데 첫 메시지 맥락에 프로젝트와 관련 작업이 이미 들어 있습니다.

### 도구 선택

- 반복 호출·잘못된 도구·인자 오류는 없었습니다.
- 재점검은 늘 `option_ids: []`(무대응)만 계산했습니다. 시스템 프롬프트가 "최종 답 전에 `option_ids []`로 재점검하라"고 지시하고, 부르지 않으면 한 번 더 요청합니다(`runtime.py:98`, `runtime.py:141`). 대응안 계산은 에이전트가 끝난 뒤 규칙이 따로 하므로(`worker.py:394` 에이전트 → `worker.py:445` 대응안 계산) 에이전트는 대응안 결과를 보지 못하고 "계산되지 않았다"고 적습니다.
- 규정 언급(H02)에도 `simulate_regulatory_condition`과 `search_risk_signals`를 부르지 않았습니다. 이번 통보에는 조건부 날짜가 없어 도구를 불렀어도 `NEEDS_INPUT`이었겠지만, 화면에는 어떤 도구를 고려했는지 남지 않습니다.
- H04 정식 분석은 `get_project_context` → `list_response_options` → 재점검 순서였고, 같은 입력의 잠정 분석은 재점검만 불렀습니다. 같은 입력에서 도구 선택이 달라집니다.

### 응답 형식 오류와 재시도

- JSON 파싱 실패, 재시도, 400/422 대체 요청은 0건입니다.
- 형식이 느슨해 생기는 문제는 많습니다(`response_format`이 `json_object`만 지정).
  - `summary`: 최종 응답 5건 모두 문자열이 아닌 객체 → 템플릿 문장으로 대체(`runtime.py:420`). 모델의 요약은 버려집니다.
  - `status`: `PENDING_HUMAN_REVIEW`, `PATCH_REVIEW_REQUIRED`, `NEEDS_REVIEW`, `REVIEW_REQUIRED`, `NEEDS_INPUT`가 그대로 저장(`runtime.py:417`).
  - `option_explanations`: 5건 중 4건이 객체 배열 → 화면이 `JSON.stringify`로 그대로 출력(`workspace.tsx:1109`). 화면에 보인 H04 정식 분석만 문자열이었습니다.
  - `regulatory_assessment`: 5건 모두 `status/assessment/…` 등 매번 다른 키. 규제 단어가 없는 통보(H04, V08)는 서버가 버리므로 출력 토큰만 쓰고, H02는 화면이 읽는 `likelihood/reason/human_check`가 비어 "-"로 표시됩니다(`runtime.py:478`, `workspace.tsx:1107`).
- 숫자 근거 필터(`runtime.py:433`, `runtime.py:473`)가 계산 결과에 없는 숫자를 지우는데, 옵션 ID `HOPT-01`의 `01`도 숫자로 보고 지워 "HOPT-은"이 됩니다.

### 사람 확인 대기가 오류처럼 보이는 곳

- 정상 완료된 분석에도 `멈춘 이유:`가 경고색(`.agent-stop`, 갈색)으로 표시됩니다(H04, H02).
- `확인 질문:`에 실제 사람 확인 항목과 사실이 아닌 "계산되지 않았습니다" 문장이 한 줄로 섞여 나옵니다.
- 공휴일 자동 분석: "판단 기록이 없습니다." + "멈춘 이유: 요청할 작업이 명시되지 않아 일정 도구를 실행하지 않았습니다." + 사용자에게 옵션 ID를 고르라는 질문.
- 공지 경로: 사람이 효력일을 넣어야 하는 정상 대기 상태가 "규칙 기반 분석 / 멈춘 이유: 적용 지역·설비 확인, 효력 발생일 또는 작업 중단 기간"으로 표시됩니다.
- 에이전트를 끈 상태의 결과가 `status: llm_unavailable`, "LLM 설정이 없어 계산 결과만 제공합니다"로 저장됩니다. 의도적으로 끈 것과 장애를 구분하지 않습니다(`worker.py:490`).

### 판단 과정이 화면에서 안 보이거나 이해하기 어려운 곳

- **켬/끔이 구분되지 않습니다.** 끈 상태에서도 같은 제목 '에이전트 판단 과정' 아래 "규칙 기반 분석"과 `도구 호출 기록 8건`(규칙이 계산한 재점검 8회, `source: rules_fallback`)이 나옵니다. 켠 상태의 기록은 3건이라 오히려 규칙 쪽이 더 많은 도구를 쓴 것처럼 보입니다.
- 패널에 LLM 사용 여부, 모델, 호출 수, 토큰, 비용, 소요 시간이 없습니다. 에이전트 상태값도 표시하지 않습니다.
- 요약 문장이 템플릿이라 켬/끔 모두 "통보의 일정 영향을 검토했습니다. 계산된 완료 예정일은 …"입니다.
- V08의 작업 연결, 공지 후보 축소처럼 실제로 가치를 낸 판단이 대응안 화면 패널에 나오지 않습니다(변경 카드에만 있음, 공지는 "규칙 기반 분석"으로 표시).
- 패널 문장이 어떤 근거(원문 인용, 계산 결과, L2 사례)에서 나왔는지 연결되지 않습니다.
- 패널이 대응안 목록·승인 패널 아래에 있어 스크롤해야 보입니다. '전체 도구 응답 보기'를 열면 22만 자 JSON이 그대로 펼쳐집니다.
- 공지 후보의 이유가 영어이고, 이유와 인용문이 구분 없이 붙어 나옵니다(`apps/web/app/external-watch.tsx:129`).

## 원인 요약

1. 공급사 통보 경로에서 에이전트가 대응안 계산 **전에** 실행되고 계산 결과를 받지 못합니다. 역할이 "계산된 대응안을 설명하고 추천"이 아니라 "무대응 재점검 후 요약"으로 정해져 있습니다.
2. 워커가 `preview_only`를 무시합니다.
3. 계산 도구가 화면용 전체 결과를 그대로 모델에 넘깁니다(모델용 요약 결과가 없음).
4. 최종 응답 형식이 강제되지 않고, 화면은 특정 키를 가정합니다.
5. 숫자 근거 필터가 ID 속 숫자까지 지웁니다.
6. 결과에 에이전트 모드·상태·사용량이 화면용으로 정리돼 있지 않고, 비공급사 경로는 공급사 기본값(`rules_only`)을 그대로 붙입니다(`worker.py:329`, `worker.py:414`).
7. 외부 변화 감지가 곧바로 유료 분석을 만듭니다.
8. 유료 상한이 호출이 아니라 실행 단위라서(`worker.py:107`) H04 한 번(실행 3건)에 호출 7회가 나가도 3건으로만 셉니다. 비용은 `UNKNOWN`으로 남고 게이트웨이가 준 실제 비용은 저장하지 않습니다.
