결론적으로 현재 REPLAN은 **AI 에이전트 시스템이 맞지만, 전체가 자율 에이전트로 돌아가는 구조는 아닙니다.**

정확한 표현은:

> 규칙 기반 감시 워커 위에, 도구를 사용하는 단일 AI 에이전트를 결합한 사람 승인형 시스템

입니다.

| 구성 | AI 에이전트인가? | 역할 |
|---|---:|---|
| 외부 출처 수집 워커 | 아니요 | 정해진 시간과 규칙으로 데이터 수집 |
| 규칙·RAG 탐지 | 아니요 | 변화와 관련 작업 후보 검색 |
| 문서 LLM 해석 | 부분적 | 문서에서 근거 있는 후보 추출 |
| 조사·대응안 검토 | 예 | LLM이 필요한 도구를 선택하고 결과를 바탕으로 다음 행동 결정 |
| 일정 반영·승인 | 아니요 | 계산기와 사람이 담당 |

## 1. 워커는 어떤 규칙으로 가져오는가

### 먼저 Excel로 감시 후보를 만듦

기준 일정 Excel을 등록하면 작업 정보를 보고 감시 계획을 제안합니다.

- 작업 국가와 기간이 있으면 해당 연도의 공휴일
- 작업명이나 `risk_tags`가 야외 작업을 나타내면 기상 감시
- `regulation`, `permitting` 태그가 있으면 규제·인허가 출처
- `supplier_id`가 있으면 공급사 휴무·가용성 확인
- 프로젝트 좌표가 있으면 해당 위치 기상정보

이 과정은 [watch_suggestions.py](/Users/shinminseo/Desktop/ai-innovators/services/api/app/watch_suggestions.py:40)에 구현돼 있습니다.

사용자는 각 제안을 다음 중 하나로 결정해야 감시를 켤 수 있습니다.

- 수락
- 수정 후 수락
- 제외

### 감시 주기 규칙

감시를 활성화하면 워커가 독립된 주기로 확인합니다.

- 기상: 기본 6시간
- 공지·RSS: 기본 12시간
- 공휴일: 기본 24시간
- 각 주기는 최소 1시간, 최대 168시간

같은 범위의 작업이 이미 대기 중이거나 실행 중이면 중복 실행하지 않습니다. 마지막 실행 후 설정 시간이 지나야 새 작업을 큐에 넣습니다.

### 기상정보 판단 규칙

Open-Meteo에서 현장 좌표의 예보를 가져온 뒤 아래 조건을 모두 만족해야 변경 신호가 생깁니다.

- 사용자가 지정한 풍속·강수량 임계값 초과

### 공휴일 판단 규칙

공휴일도 자동으로 모든 작업에 적용하지 않습니다.

- 공공 휴일 유형이어야 함
- 국가 코드가 일치해야 함
- 지역 공휴일이면 subdivision이 일치해야 함
- 사용자가 연결한 작업이어야 함
- 해당 날짜가 작업 기간과 겹쳐야 함

조건을 만족하더라도 “실제 현장이나 공급사가 쉬는 날인지 확인 필요” 상태로 생성됩니다.

### 공지·뉴스 판단 규칙

등록된 HTTPS 웹페이지나 RSS를 가져와 다음 항목을 확인합니다.

- 원문에 작업 ID가 직접 등장
- 원문에 작업명이 직접 등장
- 작업의 위험 태그가 등장
- 사용자가 설정한 `출처 + 키워드 + 작업` 조합이 일치

예를 들어 사용자가 다음과 같이 설정했다면:

```text
출처: 관세기관 공지 RSS
키워드: export license, cathode material
연결 작업: T042 양극재 통관
```

공지에 `export license`가 등장하면 T042가 영향 작업 후보가 됩니다.

이 단계에서는 공지 발행일을 지연 날짜로 사용하지 않습니다. 적용 지역, 설비, 효력일, 중단 기간은 항상 확인 대상으로 남깁니다.

근거: [external_risks.py](/Users/shinminseo/Desktop/ai-innovators/services/api/app/external_risks.py:32)

### 변경 여부 판단

수집한 문서는 해시로 이전 내용과 비교합니다.

- 내용이 같으면 새 이벤트를 만들지 않음
- 내용이 바뀌면 새 근거와 변경 신호 생성
- 동일 출처의 이전 미확정 신호는 `대체됨` 처리
- 수집 실패를 `위험 없음`으로 간주하지 않음

## 2. RAG는 어떻게 쓰이는가

새 공지나 문서를 가져오면 다음과 같이 처리합니다.

```text
원문 저장
→ 최대 1,200자 단위 passage 생성
→ 프로젝트 작업 정보로 검색어 생성
→ 관련도가 높은 passage 최대 8개 선택
→ 작업 후보와 citation ID 연결
```

검색어에는 다음이 포함됩니다.

- 작업 ID와 작업명
- 설비 ID
- 공급사 ID
- 국가·지역
- 공정 단계
- 위험 태그
- 사용자가 승인한 감시 키워드

현재는 벡터 검색이 아니라 단어와 구문 일치를 점수화하는 SQLite lexical RAG입니다.

## 3. LLM은 구체적으로 어디에 쓰이는가

### A. 감시 계획 설명 보강

Excel에서 만든 감시 후보를 LLM에 전달해서:

- 왜 이 작업을 감시해야 하는지
- 어떤 검색어가 유용할지

를 추가합니다.

하지만 LLM은 다음을 새로 만들 수 없습니다.

- 공식 출처 URL
- 기상 임계값
- 적용 날짜
- 법적 적용 여부

이 단계는 단일 LLM 호출이므로 엄밀한 의미의 에이전트 루프는 아닙니다.

### B. 외부 문서 해석

사람이 `근거·작업 후보 분석`을 누르면 LLM에 다음만 전달합니다.

- 검색된 passage
- citation ID
- 프로젝트의 활성 작업 목록
- 작업 위치·설비·공정·위험 태그

LLM은 다음 형식으로 답해야 합니다.

```json
{
  "candidates": [
    {
      "task_id": "T042",
      "quote": "원문의 정확한 인용문",
      "reason": "이 작업과 관련된 이유",
      "citation_ids": ["P-123456"]
    }
  ]
}
```

서버는 다시 검증합니다.

- 실제 존재하는 작업 ID인가
- 인용문이 원문 passage에 정확히 존재하는가
- citation ID가 해당 passage와 일치하는가

검증에 실패한 후보는 버립니다.

근거: [external_risks.py](/Users/shinminseo/Desktop/ai-innovators/services/api/app/external_risks.py:150)

### C. 도구를 사용하는 조사 에이전트

여기가 실제 AI 에이전트에 해당합니다.

사용자가 조사를 시작하면 LLM은 상황에 따라 다음 도구를 선택할 수 있습니다.

- `find_procurement_items`: 같은 공급사·원산지의 다른 구매 품목 찾기
- `get_task_facts`: 작업의 공급사·통관·인허가 정보 확인
- `check_schedule_slack`: 해당 작업이 며칠 지연을 흡수할 수 있는지 계산
- `simulate_conditional`: 공지 조건이 적용된다는 가정하에 일정 계산
- `compare_responses`: 대응안별 완료일과 비용 비교
- `search_risk_signals`: 저장된 실제 유사 사례 검색
- `narrow_candidates`: 작업 후보가 많을 때 인용 기반으로 후보 축소

흐름은 다음과 같습니다.

```text
LLM이 현재 상황 확인
→ 필요한 도구 하나 선택
→ 서버가 도구 실행
→ 결과를 LLM에 반환
→ LLM이 다음 도구 또는 중단 결정
→ 구조화된 조사 결과 생성
```

에이전트는 조사에서 최대 6단계, 전체 도구 호출은 최대 8회까지만 실행합니다.

## 4. 에이전트는 언제 멈추는가

조사 에이전트에는 명시적인 중단 상태가 있습니다.

| 상태 | 의미 |
|---|---|
| M1 | 외부 신호와 프로젝트 변경 원인이 관련 없음 |
| M2 | 관련은 있지만 프로젝트 완료일에는 영향 없음 |
| M3 | 적용 기간이나 지연 기간이 원문에 없음 |
| M4 | 공급사·담당자 등 사람의 사실 확인 필요 |
| M5 | 입력 부족으로 계산 불가 |
| done | 영향과 대응안 비교 완료 |

정보가 부족하면 억지로 결론을 내리지 않고 질문 하나와 협력사 확인 메일 초안을 생성한 뒤 멈춥니다. 메일을 직접 발송하지는 않습니다.

## 5. 에이전트 안전장치

현재 에이전트에는 다음 제한이 들어가 있습니다.

- `commit`, `send` 이름이 포함된 도구 실행 금지
- 작업과 날짜가 확정되지 않으면 일정 계산 도구 제거
- 같은 도구와 인자를 반복 호출하면 중단
- 등록되지 않은 도구 호출 차단
- 다른 프로젝트 ID 접근 차단
- 도구 인자 타입과 크기 검증
- 일정·비용 숫자는 계산기 결과에 있는 값만 최종 문장에 허용
- LLM이 만든 규제 확정 판단을 그대로 사용하지 않음
- 미래에 발행된 사례는 당시 판단 근거가 아닌 참고자료로만 표시
- LLM 장애가 나도 기존 계산 결과는 유지

## 6. AI 에이전트 서비스가 맞는가

판단은 다음과 같습니다.

### 맞는 부분

LLM이 단순히 문장을 생성하는 데 그치지 않고:

- 목표를 전달받고
- 현재 프로젝트 맥락을 읽고
- 사용 가능한 도구 중 하나를 선택하고
- 도구 결과를 관찰하고
- 다음 조사 행동을 결정하고
- 중단 조건에 따라 종료

하기 때문에 조사·검토 부분은 분명한 **도구 사용형 AI 에이전트**입니다.

### 아닌 부분

다음은 에이전트가 아니라 결정론적 시스템입니다.

- 감시 주기 결정
- 외부 데이터 수집
- 해시 비교와 중복 제거
- 기상 임계값 판단
- 공휴일 적용 후보 계산
- 일정 및 비용 계산
- 승인과 일정 반영

따라서 전체 제품을 “자율 AI 에이전트”라고 소개하면 과장입니다.

가장 정확한 표현은:

> REPLAN은 외부 변화를 규칙과 RAG로 감지하고, AI 에이전트가 필요한 조사를 도구 기반으로 수행하며, 사람이 승인한 정보만 일정에 반영하는 프로젝트 리스크 대응 시스템이다.

## 에이전트 설계 구조

현재 구조를 에이전트 관점으로 정리하면 다음과 같습니다.

```text
[감각기관]
워커·외부 API·문서 업로드
        ↓
[기억]
원문 스냅샷·passage·이벤트·일정 버전
        ↓
[1차 필터]
규칙·해시 비교·lexical RAG
        ↓
[두뇌]
외부 LLM 에이전트
        ↓
[도구]
작업 조회·구매 품목 조회·여유 계산·조건부 시뮬레이션
        ↓
[행동 제한]
질문·설명·메일 초안까지만 가능
        ↓
[승인권자]
프로젝트 운영팀
        ↓
[실행]
일정 버전 확정·Excel 내보내기
```

이 서비스에는 **“LLM이 모든 것을 자율적으로 수행하는 에이전트”보다 지금과 같은 제한된 단일 에이전트가 더 적합합니다.** 일정과 비용은 정확성이 중요하므로 LLM은 조사 순서와 의미 해석을 담당하고, 실제 계산과 반영은 도구와 사람에게 남겨두는 구조가 맞습니다.

확실하지 않은 부분은 실제 배포 서버에서 LIVE LLM 설정이 활성화돼 있는지입니다. 코드상 외부 LLM 연결은 완성돼 있지만, 현재 서버의 API 키·게이트웨이·유료 호출 활성화 상태는 저장소만으로 확인할 수 없습니다.
